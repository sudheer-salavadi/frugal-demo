<img src="/public/blog/image/best-practices-optimize-cloud-datadog-logging-costs/1.png" alt="Best Practices to Optimize Cloud Datadog Logging Costs"><p>Datadog logs are valuable for troubleshooting, security, and operational visibility. They can also become a significant cloud cost when every application emits verbose events, large payloads, and duplicate telemetry.</p><p>The goal is not to stop collecting logs. It is to send the right logs, at the right level of detail, to the right destination, for the right amount of time. This guide outlines practical ways cloud engineering and SaaS development teams can reduce Datadog logging costs without compromising incident response.</p><h2>Start by understanding where Datadog logging costs come from</h2><p>Before changing configuration, identify the sources of your logging spend. Common cost drivers include:</p><ul><li><p>High log volume from production services, background workers, and serverless functions.</p></li><li><p>Verbose debug or trace logging left enabled in production.</p></li><li><p>Large log records containing request bodies, stack traces, headers, or duplicated context.</p></li><li><p>Logs indexed for search when they only need short-term access or archival.</p></li><li><p>Long retention periods for logs that are rarely queried.</p></li><li><p>Repeated events generated by retries, health checks, polling, or noisy dependencies.</p></li><li><p>Multiple observability tools receiving the same events.</p></li></ul><p>Datadog billing models and product names can change, so confirm current pricing, retention, and indexing details in your account and the <a href="https://www.datadoghq.com/pricing/" rel="nofollow">Datadog documentation</a>. The optimization principles remain useful regardless of the specific plan.</p><h2>1. Measure log volume before optimizing it</h2><img src="/public/blog/image/best-practices-optimize-cloud-datadog-logging-costs/2.png" alt=""><p>Cost reduction is easier when teams can connect usage to services and code paths. Create a baseline for each environment and service, including daily ingestion, indexed volume, retention, and the highest-volume sources.</p><p>Useful dimensions include service, environment, log level, source, region, status code, and endpoint. Look for services with unusually high event counts or large average record sizes. A small number of chatty services often accounts for a disproportionate share of total volume.</p><p>Frugal is designed to connect source code, cloud, observability, and billing data so teams can identify the code driving cloud and AI costs. This can help move the conversation from “Datadog is expensive” to “this endpoint emits 40,000 low-value events per hour.”</p><h2>2. Set appropriate log levels by environment</h2><p>Debug logs are useful during development and incident investigation, but they should not be the default for every production request. Use environment-specific configuration and make temporary increases deliberate, time-bound changes.</p><pre><code>LOG_LEVEL=info</code></pre><p>In application code, reserve each level for a clear purpose:</p><ul><li><p><strong>error:</strong> failures that require investigation or affect a request, job, or user.</p></li><li><p><strong>warn:</strong> unusual conditions that are handled but may indicate a problem.</p></li><li><p><strong>info:</strong> meaningful lifecycle or business events needed for operations.</p></li><li><p><strong>debug:</strong> detailed diagnostic information, normally disabled in production.</p></li></ul><p>Avoid logging the same failure at every layer. If a lower-level function records an exception and the request handler records the complete exception again, one failure can create several large records.</p><h2>3. Reduce log volume at the source</h2><p>Datadog pipelines can process logs after they are emitted, but the most effective savings usually come from preventing unnecessary events and fields from being generated in the first place.</p><p>Review recurring sources of noise:</p><ul><li><p>Successful health checks and readiness probes.</p></li><li><p>Routine polling messages.</p></li><li><p>Repeated retry attempts that contain no new diagnostic information.</p></li><li><p>Full request and response payloads.</p></li><li><p>Static configuration values repeated on every event.</p></li><li><p>Low-value framework messages emitted at info level.</p></li></ul><p>Replace repetitive messages with counters or metrics when you need aggregate visibility rather than individual event detail. For example, a request count and error count may be more useful and less expensive than logging every successful request.</p><h2>4. Sample high-volume, low-value events</h2><img src="/public/blog/image/best-practices-optimize-cloud-datadog-logging-costs/3.png" alt=""><p>Sampling is useful when retaining every event provides little operational value. Apply it selectively. Do not sample away security events, payment failures, authorization failures, or logs required for compliance.</p><p>A simple application-level approach might look like this:</p><pre><code>const shouldLogRequest = (request) =&gt; {
  const alwaysKeep = request.statusCode &gt;= 400 || request.path.startsWith(&#39;/admin&#39;);
  const sampleRate = 0.05;

  return alwaysKeep || Math.random() &lt; sampleRate;
};

if (shouldLogRequest(request)) {
  logger.info({
    service: &#39;api&#39;,
    route: request.route,
    status_code: request.statusCode,
    duration_ms: request.durationMs
  }, &#39;request completed&#39;);
}</code></pre><p>Use deterministic sampling where possible so related events can be retained together. For example, sample by request ID, trace ID, tenant, or user session rather than independently sampling every line.</p><h2>5. Keep structured logs compact</h2><p>Structured logging improves search and automation, but adding every available field to every event increases payload size and processing cost. Keep common fields concise and avoid duplicating large objects.</p><p>Prefer a summary over a complete payload:</p><pre><code>logger.info({
  order_id: order.id,
  item_count: order.items.length,
  total_cents: order.totalCents,
  payment_status: payment.status
}, &#39;order payment completed&#39;);</code></pre><p>Avoid logging passwords, tokens, authorization headers, personal data, and complete request bodies. Redaction protects users and reduces the size of records that should never have been collected.</p><h2>6. Separate indexed logs from archived logs</h2><p>Not every log needs to be immediately searchable. Define categories based on how the data is used:</p><ul><li><p><strong>Operational logs:</strong> recent errors and events needed for active troubleshooting.</p></li><li><p><strong>Security logs:</strong> authentication, authorization, and access events subject to your security requirements.</p></li><li><p><strong>Audit logs:</strong> records that must be retained for governance or compliance.</p></li><li><p><strong>Diagnostic logs:</strong> detailed information useful during short-term investigations.</p></li><li><p><strong>Low-value logs:</strong> routine events that may be sampled, excluded, or stored outside the primary observability workflow.</p></li></ul><p>Review index filters and exclusion rules regularly. A log does not need to be indexed forever to remain available for an investigation or retention requirement. Use archival and restoration workflows where they meet your operational and compliance needs.</p><p>For a deeper look at managing observability spend, see Frugal’s guide to <a href="https://frugal.co/blog/the-frugal-approach-to-datadog-log-management-costs" rel="nofollow">the Frugal approach to Datadog log management costs</a>.</p><h2>7. Control retention by data value</h2><img src="/public/blog/image/best-practices-optimize-cloud-datadog-logging-costs/4.png" alt=""><p>Long retention is expensive when applied uniformly. Set retention based on how quickly a log loses operational value and whether another system already preserves it.</p><p>For example, recent application errors may need fast access, while older diagnostic events may be useful only during a defined incident review window. Security and audit data should follow your organization’s documented requirements rather than an arbitrary default.</p><p>Document the retention decision for each log category. This prevents teams from extending retention “just in case” and makes future reviews faster.</p><h2>8. Filter and transform logs with care</h2><p>Use collection and processing rules to remove known noise, redact sensitive fields, and normalize attributes. Apply exclusions carefully and test them against real incident scenarios.</p><p>A practical review checklist includes:</p><ul><li><p>Can the team still investigate failed requests after this filter is enabled?</p></li><li><p>Are important status codes, trace IDs, and service identifiers preserved?</p></li><li><p>Could the rule remove evidence needed for security investigations?</p></li><li><p>Does the rule match only the intended environment or service?</p></li><li><p>Is the rule documented and owned by a specific team?</p></li></ul><p>Do not use a broad exclusion as a substitute for fixing a noisy logger. If a service emits excessive events, update its configuration or code and use the pipeline as a safety net.</p><h2>9. Avoid duplicate telemetry</h2><img src="/public/blog/image/best-practices-optimize-cloud-datadog-logging-costs/5.png" alt=""><p>Duplicate logs often appear when an application, container runtime, cloud service, and sidecar each emit records for the same event. Map the logging path from source to destination and identify where duplication occurs.</p><p>Pay special attention to:</p><ul><li><p>Application logs collected by both an agent and a cloud integration.</p></li><li><p>Load balancer or API gateway logs copied into multiple destinations.</p></li><li><p>Retries that cause one failure to be recorded by several libraries.</p></li><li><p>Logs forwarded through an intermediate platform before reaching Datadog.</p></li><li><p>Separate development and production collectors using overlapping tags or routes.</p></li></ul><p>Preserve the copy that provides the best operational value and required context. Then remove or reduce redundant copies after validating the change.</p><h2>10. Create ownership and budgets for logging</h2><p>Logging costs grow when no team owns the decision to emit, index, and retain data. Assign ownership at the service level and include logging in service reviews.</p><p>Useful controls include:</p><ul><li><p>Monthly log-volume reviews by service owner.</p></li><li><p>Alerts for unexpected ingestion growth.</p></li><li><p>Maximum event-size guidance.</p></li><li><p>Production log-level standards.</p></li><li><p>Approval for temporary debug logging.</p></li><li><p>Cost checks in service and infrastructure changes.</p></li></ul><p>Cost controls work best when they are part of the development workflow. Frugal generates reviewable pull requests that help teams reduce waste and build cost controls into code changes, rather than relying only on a monthly billing review.</p><h2>11. Connect logging changes to application code</h2><p>A dashboard can show that log volume increased. It may not show which code change introduced the increase. Review logging changes alongside deployments, dependency updates, feature flags, and traffic changes.</p><p>Ask focused questions during incident and cost reviews:</p><ul><li><p>Which service or code path generated the additional events?</p></li><li><p>Did a new retry loop, middleware component, or framework upgrade change volume?</p></li><li><p>Did a field expansion increase average event size?</p></li><li><p>Was a debug setting enabled by a deployment or configuration change?</p></li><li><p>Can the same operational signal be represented with a metric or trace?</p></li></ul><p>This approach aligns logging optimization with broader cloud cost engineering. Frugal’s perspective on <a href="https://frugal.co/blog/why-cloud-cost-optimization-isn-t-enough" rel="nofollow">why cloud cost optimization is not enough</a> is relevant here: durable savings require changes in the systems and workflows that create spend.</p><h2>A practical Datadog logging optimization checklist</h2><ol><li><p>Baseline ingestion, indexing, retention, and average event size by service.</p></li><li><p>Disable production debug logging unless it is explicitly needed.</p></li><li><p>Remove health-check, polling, and duplicate success events.</p></li><li><p>Sample high-volume events while preserving errors and security signals.</p></li><li><p>Redact sensitive data and remove unnecessary large fields.</p></li><li><p>Review index filters, exclusion rules, and archival workflows.</p></li><li><p>Set retention according to operational and compliance requirements.</p></li><li><p>Trace duplicate collection paths across applications, agents, and cloud integrations.</p></li><li><p>Assign ownership and alert on unexpected log growth.</p></li><li><p>Review logging changes as part of pull requests and deployments.</p></li></ol><h2>Conclusion</h2><p>Optimizing Datadog logging costs is not about collecting less information indiscriminately. It is about improving the signal-to-noise ratio of your observability data.</p><p>Start with the services that generate the most volume, fix unnecessary logging at the source, sample only low-value events, and align indexing and retention with how teams actually investigate incidents. When cloud, observability, billing, and source-code data are reviewed together, engineering teams can reduce waste while keeping the visibility they need to operate confidently.</p>
