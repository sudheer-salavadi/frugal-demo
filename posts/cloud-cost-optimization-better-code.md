<img src="/public/blog/image/cloud-cost-optimization-better-code/cloud-cost-optimization-better-code-1.png"><h2>Cloud cost optimization starts where spend is created</h2><p>Cloud cost optimization is often treated as a finance exercise: review a billing report, identify an expensive service, and ask engineering teams to reduce usage. That approach can reveal where money is going, but it rarely explains why the cost exists or which code change will reduce it.</p><p>The more useful question is: which parts of the application are driving cloud spend, and what can engineers change without compromising reliability or customer experience?</p><p>Frugal connects source code, cloud, observability, and billing data to help teams trace cloud and AI costs back to the code that creates them. This gives cloud engineering and SaaS development teams a practical path from cost visibility to reviewable improvements.</p><h2>Why traditional cost optimization struggles</h2><p>Cloud bills describe resources, services, regions, and usage patterns. Application code describes requests, jobs, features, and business workflows. These systems are related, but they are not automatically connected.</p><p>Without that connection, teams commonly run into three problems:</p><ul><li><p><strong>Resources are easier to identify than owners.</strong> A database, log stream, or compute workload may serve multiple applications and teams.</p></li><li><p><strong>Cost anomalies arrive after the design decision.</strong> Engineers may discover an inefficient query, excessive logging, or an expensive API call only after usage has grown.</p></li><li><p><strong>Optimization advice is too broad.</strong> “Reduce storage” or “use fewer requests” does not provide a safe, reviewable change in a codebase.</p></li></ul><p>These challenges are part of why cloud cost optimization cannot be reduced to buying discounts or deleting unused resources. Read <a href="https://frugal.co/blog/why-cloud-cost-optimization-isn-t-enough" rel="nofollow">why cloud cost optimization is not enough</a> for a broader view of the engineering work involved.</p><h2>A practical framework for cloud cost optimization</h2><h3>1. Establish a reliable cost baseline</h3><p>Start by understanding current spend across the services and workloads that matter most. Look for trends, usage drivers, and changes over time rather than focusing only on a single monthly total.</p><p>A useful baseline should connect cost data with operational context, including:</p><ul><li><p>Service and resource usage</p></li><li><p>Application or workload ownership</p></li><li><p>Request, job, or transaction volume</p></li><li><p>Performance and reliability indicators</p></li><li><p>Relevant source code and deployment changes</p></li></ul><p>This context helps teams distinguish unavoidable growth from waste introduced by configuration, architecture, or application behavior.</p><h3>2. Find the code behind expensive usage</h3><p>Once a high-cost service or workload is visible, trace it to the code paths that create the usage. Examples might include a query executed too frequently, an oversized payload, an unbounded retry loop, or logs emitted at a level that is not appropriate for production.</p><p>The goal is not to optimize everything. It is to identify changes with a clear relationship between engineering effort, expected savings, and operational risk. Frugal’s perspective on prioritization is covered in <a href="https://frugal.co/blog/why-not-just-optimize-everything" rel="nofollow">why teams should not just optimize everything</a>.</p><h3>3. Turn recommendations into reviewable changes</h3><p>Cost recommendations are most useful when they fit the same workflow as other engineering improvements. A proposed change should explain the cost driver, show the relevant code or configuration, and make its tradeoffs clear.</p><p>Frugal generates reviewable pull requests designed to help teams reduce waste through familiar development processes. Engineers can inspect the proposed change, test it, and decide whether it is appropriate for the application.</p><h3>4. Measure the result after deployment</h3><p>Optimization is incomplete until the result is measured. Compare usage, cost, performance, and error behavior after a change reaches production. A lower bill is valuable, but not if it comes with degraded reliability or a poor customer experience.</p><p>For observability-heavy environments, review cost drivers across metrics and logs as well as compute and storage. Frugal’s guides to <a href="https://frugal.co/blog/the-frugal-approach-to-gcp-cloud-monitoring-metrics-costs" rel="nofollow">GCP monitoring and metrics costs</a> and <a href="https://frugal.co/blog/the-frugal-approach-to-datadog-log-management-costs" rel="nofollow">Datadog log management costs</a> provide useful examples of how telemetry choices can affect spend.</p><h2>High-impact areas to investigate</h2><p>The right priorities depend on the application, but several patterns appear frequently in cloud cost optimization work:</p><ul><li><p><strong>Data access:</strong> inefficient queries, excessive reads, missing pagination, and unnecessary data movement.</p></li><li><p><strong>Compute usage:</strong> workloads that run more often, longer, or at a larger size than required.</p></li><li><p><strong>Storage:</strong> data retained indefinitely, duplicated across systems, or stored at an unsuitable tier.</p></li><li><p><strong>Observability:</strong> high-volume logs and metrics that provide limited operational value.</p></li><li><p><strong>Third-party and AI APIs:</strong> repeated calls, oversized prompts, avoidable retries, or expensive model selection.</p></li><li><p><strong>Architectural defaults:</strong> settings chosen for convenience that no longer match production usage.</p></li></ul><h2>Build cost controls into the development workflow</h2><p>Cloud cost optimization becomes more durable when it is part of normal software delivery rather than a periodic cleanup project. Teams can add cost-aware checks to design reviews, pull requests, service ownership, and post-deployment measurement.</p><p>Effective controls should be specific enough to guide decisions without blocking legitimate product development. Examples include:</p><ul><li><p>Reviewing expected cost impact for new high-volume workflows</p></li><li><p>Assigning clear ownership to major cost centers</p></li><li><p>Monitoring cost per request, job, or customer where practical</p></li><li><p>Setting alerts for unusual usage patterns</p></li><li><p>Revisiting logging, retention, and data access choices as systems scale</p></li><li><p>Using automated suggestions that engineers can review before adoption</p></li></ul><p>Security and access design matter as well. Frugal emphasizes read-only access, encryption, and private deployment options so teams can evaluate cost data within appropriate operational controls.</p><h2>The next step for engineering teams</h2><p>Cloud cost optimization is most effective when it connects financial outcomes to technical decisions. Billing data can show that spend increased. Observability can show when behavior changed. Source code can reveal what to change. Bringing these signals together helps teams make targeted improvements instead of broad, disruptive cuts.</p><p>A practical starting point is to select one high-cost workload, map its usage to the responsible code, propose a small change, and measure the outcome. Repeat that process consistently, and cost control becomes part of how the team builds and operates software.</p>
